# Linked background videos — versions 116–118

Open **Backgrounds / video**, paste a direct HTTPS video URL into **Or paste a video link**, then choose **Use video link** or press Enter. Version 117 also accepts YouTube short, watch, Shorts, live and embed links. Link feedback is visible directly below Use video link. MP4/H.264 and WebM are recommended for file links. Signed URLs and URLs without an extension can be used if they return a playable video. Vimeo, TikTok and other unsupported video-page URLs are rejected; the form explains this and leaves the current source intact for rejected links.

Linked videos use the existing muted video player and inline preview. The chart's first-note anchor, offset, pause/resume, restart, practice speed and section timing all remain controlled by the song clock. Loading/seek preparation happens before audio starts. A blocked, expired, inaccessible or incompatible link reports recovery guidance. Playback still depends on the hosting server and browser codec support. Selecting a URL requests that video from its host in the player's browser; it does not upload song audio or download remote video bytes into setlist storage.

The URL, mode, offset and darkness are saved per song. **Save video link to setlist** commits the pairing, and the row says **Video link saved**. Uploaded videos retain their existing local/offline storage and labels. A link requires internet access and continued access to the same address. Replacing a saved uploaded video with a link releases that video's old storage chunks after the new reference commits. Malformed stored links are not applied.

**Save chart + video link backup** exports the song audio, all charts and URL/timing. It does not contain the linked video's bytes. The RIFFPACK2 background metadata contains a validated `url` and zero video bytes. Import validates the source and exact payload lengths, restores the pairing and explains the internet requirement. Existing RIFFPACK1 and file-video RIFFPACK2 backups remain supported. Link backups require version 116 or later; regular Export current song retains its chart/audio-only behavior.

Validation covers safe URL parsing, signed query preservation, rejected schemes/page links, file/link switching and object-URL ownership, per-song reopening, actual IndexedDB metadata/chunk cleanup, source-specific setlist labels, real URL-form wiring, all four instruments' first-note/pause/practice timing, exact backup/import round trips, storage/decoder errors, and existing local-video/update/pause regressions. No supported browser QA surface was available, so playback from a real user-selected host still needs a device check.


## YouTube transport in versions 117–118

The user recording showed a valid `youtu.be` link rejected by version 116. The error was reported below the visible part of the long dialog. The form now accepts that URL family, normalizes the video ID and shows status/errors beside the button.

YouTube uses the official IFrame Player API, loaded only when a YouTube background is selected. No YouTube media is downloaded or extracted. The embed includes the site origin, an origin referrer policy and autoplay permission; it starts cued and muted. The same saved URL/timing metadata and zero-video-byte RIFFPACK2 format retain this source through reopening and import.

Version 118 fixes the recorded v117 failure: a valid saved link stalled on **Matching start frame**, then reported that YouTube was still buffering or seeking. An unstarted/cued YouTube player can report zero current time and duration until playback. Seeking and immediately pausing that player can also interrupt its initial load. The adapter now uses `cueVideoById` with the selected start position and waits for a fresh `CUED` event. It does not require a decoded frame, nonzero duration or a current-time acknowledgement before starting the chart. The announcement says **Queuing YouTube video**. Preparation failures also appear beside Use video link.

The adapter verifies the actual supported playback rate after cueing (which resets the rate), then schedules song audio. No seek/play command disturbs the queued position during count-in or a negative offset. `playVideo` is called at the first-note trigger, even if duration is still unknown. Pause/resume, restart and section launches queue their own position. Stale loading callbacks cannot revive a removed/replaced source. While playing, drift corrections are throttled and skipped during buffering to avoid continuous seek commands. Other backgrounds retain the native video player.

YouTube starts/seeks may land near a keyframe, and buffering or ads can affect apparent sync. Cueing confirms a queued position, not a decoded starting frame; the thumbnail can remain visible until playback begins. Running correction tolerates 650 ms and is limited to once per second except transport boundaries. This is not frame-exact video synchronization. Local/direct videos retain their tighter native-player behavior. A practice rate not returned by YouTube is rejected with the available choices rather than silently using a different speed. Private, embedding-disabled, autoplay-blocked, API-load and missing-referrer errors have specific recovery messages. Another video or a local file may be required.

Official API reference: https://developers.google.com/youtube/iframe_api_reference (queue/seek behavior, metadata availability, supported rates, errors and autoplay events). Deterministic tests exercise the official player calls and real Riffbound UI handlers using adapters, including zero metadata/time before play, asynchronous cue acknowledgement, cue cancellation/timeouts, held starts and rate resets. A supported browser QA surface was unavailable; the user's exact video could not be verified live from this environment, so an affected-device playback check remains necessary.
